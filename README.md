# TaskFlow 2.0 — 다중 사업 과업관리

사업명 → 지원항목 → 세부과업 → 실행단계를 선으로 연결하는 웹 관리 도구입니다.

## 1. 사이트 공개 (GitHub Pages)
저장소 **Settings → Pages**로 이동한 후 **Build and deployment → Source: Deploy from a branch → Branch: main → /(root) → Save**를 선택합니다.
공개 주소: https://kiesi10041-jpg.github.io/TaskFlow/

> GitHub Pages 설정은 사용자가 GitHub에서 한 번 활성화해야 합니다. `index.html` 파일은 이미 저장소에 있습니다.

## 2. Supabase 데이터베이스 준비
[Supabase 대시보드](https://supabase.com/dashboard)에서 이 TaskFlow에 사용할 프로젝트를 연 뒤 왼쪽 **SQL Editor → New query**로 이동합니다.
저장소의 [supabase_setup.sql](./supabase_setup.sql) 파일 전체 내용을 붙여 넣고 **Run**을 실행합니다.
**Table Editor**에서 `public.taskflow_store` 테이블이 생성됐는지 확인합니다.

## 3. API 연결
Supabase **Project Settings → API Keys**에서 **publishable key**(`sb_publishable_...`)를 확인합니다. 프로젝트 URL은 Overview 또는 Connect에서 확인합니다.
TaskFlow 사이트 왼쪽 아래 **☁ 클라우드 저장 연동**을 열고 아래 항목을 입력합니다.
- 프로젝트 URL: `https://프로젝트참조.supabase.co`
- Publishable key (`sb_publishable_...`)
- 사용할 이메일 및 비밀번호

처음 사용하는 계정이면 **계정 등록**을 누릅니다. 이메일 인증을 요구하는 경우 메일 인증 후 **로그인**을 누릅니다. 이미 Auth에 계정이 있으면 **로그인**만 하세요.

**secret key(`sb_secret_...`), service_role 키를 입력하거나 저장소에 게시하지 마세요.**

## 4. 첫 동기화 및 다른 기기
1. 웹사이트에서 **JSON 백업**으로 파일을 하나 저장합니다.
2. Supabase 계정으로 로그인하고 **현재 데이터를 클라우드에 처음 저장할까요?** 확인창에서 동의합니다.
3. 사업 하나를 수정하고 왼쪽 아래 저장 상태가 **기기 + 클라우드 저장됨**인지 확인합니다.
4. 다른 기기에서 동일 URL과 publishable key로 같은 이메일에 로그인합니다. 클라우드의 기존 사업을 **불러오기**로 승인합니다.
5. 다른 기기에 기존 자료가 있다면 불러오기 전에 각각 JSON으로 백업합니다.


## 5. TaskFlow 최신 화면 기능 (2026-11)
- **관리자 · 설정**: 왼쪽 메뉴 아래에서 개인 계정과 Supabase 동기화 상태, 전체 사업 통계를 확인합니다.
- **비상 데이터 관리**: 기존 JSON 백업/복원 버튼은 메인 화면에서 제거하고 관리자 화면 안의 접기/펼치기 메뉴로 옮겼습니다.
- **사업 구조 복제**: 사업 카드의 **사업 복제**, 사업 상세 상단 **사업 복제**, 또는 관리자 화면의 **이 사업 복제** 버튼을 선택합니다. 새 사업명과 업체명을 입력하고 원본 구조를 복제합니다.
  - **구조만 복제**: 모든 실행단계와 하위 구조를 복사하고 상태·담당자·기한·메모를 초기화합니다(새 업체 기본값).
  - **전체 복제**: 현재 진행상태와 기록까지 동일하게 복사합니다. 업체별 기밀 메모가 섞이지 않도록 주의하세요.
- **하위 단계 무제한 확장(최대 25단계 검증 한도)**: 연결형 구조도에서 단계 카드의 ＋ 버튼을 누르면 해당 단계 아래에 다음 단계가 추가됩니다. 상세 화면에서도 하위 단계 옆 ＋ 버튼으로 가지를 추가할 수 있습니다.
- **실제 데이터 유지**: 저장 형식을 변경하지 않아 기존 브라우저와 클라우드의 데이터는 이전 버전과 호환됩니다. 신규 브라우저는 불필요한 예시 사업 대신 빈 목록으로 시작합니다.

**주의:** 관리자 메뉴는 개인 사용 편의성을 위한 화면입니다. 웹사이트 자체의 별도 서버 로그인/관리자 권한 제어를 의미하지 않습니다. 온라인 자료는 Supabase 로그인 및 Row Level Security로 보호되며, 같은 브라우저의 로컬 캐시는 기기 접근 권한에 따라 보호됩니다. 클라우드 로그인이 완료되지 않으면 기기에만 저장됩니다.

## 운영상 주의
- 이 시제품은 사용자별 하나의 JSON 문서로 사업 전체를 저장합니다. **한 번에 한 기기에서 수정**하세요. 여러 기기 동시 편집은 마지막 저장 내용으로 덮일 수 있습니다.
- 브라우저 저장은 보조 저장입니다. 수시로 JSON 백업을 내려받으세요.
- 저장이 실패하면 화면에서 **클라우드 오류**를 확인하고 Supabase **Table Editor**에서 해당 계정 행의 갱신시간을 확인하세요.
- GitHub Pages는 정적 웹사이트를 공개합니다. 로그인한 사용자의 사업 데이터는 Supabase의 RLS 정책으로 구분됩니다.


## 6. TaskFlow 3.0 — 회사 공동 작업공간 (2026-11 추가)

개별 직원이 로그인해 **같은 프로젝트를 공동으로 관리**하는 기능을 제공합니다.
회사 작업공간이 설정되기 전에는 기존 개인별 저장 모드가 계속 동작합니다.

### 최초 설정 — Supabase SQL을 반드시 1회 실행

1. **기존 데이터 백업:** TaskFlow > 관리자 설정 > 비상 데이터 관리 > JSON 백업
2. 기존에 사용 중인 **동일한 Supabase 프로젝트**를 엽니다. (새 DB를 만들 필요는 없습니다.)
3. Supabase Dashboard > **SQL Editor > New query**로 이동합니다.
4. [supabase_team_v3.sql](./supabase_team_v3.sql)의 내용을 전체 복사해 **Run**으로 실행합니다.
5. 성공하면 TaskFlow 사이트를 새로고침하고 기존 관리자 이메일로 로그인합니다.
6. **관리자 설정 > 회사 공동 작업공간 시작**에서 회사명을 입력하여 생성합니다.
7. **기존 사업 가져오기** 버튼을 눌러 기존 개인 계정 데이터를 **회사 작업공간으로 복사**합니다. 기존 개인 데이터는 삭제되지 않습니다.
8. 직원 초대 코드를 발급하고, 직원이 **자신의 이메일 계정으로 로그인하여 코드로 참여**하도록 안내합니다.
9. 연결형 구조도에서 **수행과업(예: 마케팅)**을 클릭하고 오른쪽 **수행과업 참여 팀원**에서 B·C팀원을 배정합니다.

**SQL Editor 실행은 Supabase 관리자 권한이 필요한 1회 수동 작업입니다. GitHub에 코드를 올리는 것만으로 DB 테이블이 자동 설치되지는 않습니다.**

### 권한 체계

| 사용자 | 열람 | 작성·수정 |
| --- | --- | --- |
| 최고관리자(admin) | 회사의 모든 프로젝트 | 전체 프로젝트·수행과업·세부과업·팀원 배정 |
| 팀장 / PM(lead) | 회사의 모든 프로젝트 | 프로젝트·수행과업 생성, 팀원 배정, 하위과업 전체 관리 |
| 참여 팀원(member) | 참여자로 배정된 프로젝트 | **배정받은 수행과업 아래** 세부과업·실행단계·하위단계 생성 및 상태 수정 |

기존의 **사업 → 지원항목(수행과업) → 세부과업 → 실행단계 → 하위단계** 트리 구조와 완료율 계산은 동일합니다.
예: A팀장이 '스케일업' 사업을 등록하고 '마케팅'을 만들면, 배정된 B·C팀원은 각자 로그인해 블로그·영상 세부과업을 직접 등록합니다.

### 협업 동기화와 안전성

- 기존 v2의 **사용자당 전체 사업 JSON 1개**와 달리, v3는 **개별 노드(과업)별 별도 행**으로 저장해 서로 다른 과업 수정 시 덮어쓰기를 줄입니다.
- 같은 노드를 동시에 수정하면 **revision 충돌 감지**로 무단 덮어쓰기를 방지합니다.
- 화면은 약 **15초 간격으로 공동 작업 변경을 확인**합니다. (실시간 웹소켓은 아직 미지원)
- DB의 RLS가 관리자·팀장·수행과업 참여자의 편집 범위를 검사합니다. 화면의 버튼 숨김만으로 보안을 구현하지 않습니다.
- 신규 DB를 설치하기 전에는 팀 기능을 활성화할 수 없으며, 기존 개인 데이터는 유지됩니다.
- 여러 직원이 같은 과업을 동시에 편집하는 경우 한쪽 수정이 충돌로 차단될 수 있습니다. 변경 내용을 확인한 뒤 다시 저장하세요.
- 다른 계정과 공동 비밀번호를 사용하지 마세요. 직원은 각자의 Supabase Auth 계정을 사용합니다.
- GitHub Pages는 공개 정적 호스팅이므로 Supabase **service_role** 키 또는 **secret key**를 절대 저장소에 넣지 마세요.

### 유의 사항

- 현재 버전은 한 로그인 계정당 첫 번째로 연결된 공동 작업공간을 사용합니다.
- 기존 JSON 백업의 **공동 작업공간 전체 복원은 제한**됩니다. 실수로 직원의 변경을 덮어쓰지 않기 위해서입니다.
- 인터넷 연결 실패나 계정 확인 전에는 팀 자료의 편집을 잠그고, 로컬 캐시는 계정 식별 정보로 구분합니다.
- 실제 SQL 실행 및 사용자 계정·초대 테스트는 별도로 수행해야 합니다. 새 스키마 설치 전 사이트에서는 공동 작업 기능이 동작하지 않습니다.


## 7. TaskFlow 3.1 — 최고관리자 지정·인계 및 직원 명부

[**3.1 권한·직원정보 추가 SQL**](./supabase_team_v3_1.sql)은
`supabase_team_v3.sql`을 실행한 **동일한 Supabase 프로젝트**의
**SQL Editor**에서 추가로 실행해야 합니다. 기존 사업 데이터와
`taskflow_store`는 삭제하지 않으며 직원 프로필에 소속팀·직급을 추가합니다.
**3.0 SQL을 이미 실행했다면 다시 실행할 필요 없이 3.1만 적용하세요.**

### 관리자 최초 개설

- 최고관리자 최초 개설을 허용하는 로그인 이메일은 현재
  `zotozo12@naver.com`으로 지정되어 있습니다.
- 이 조건은 공개 웹사이트의 버튼 표시뿐 아니라 **Supabase RLS와
  보안 함수로 검증**합니다. 직원의 이메일 계정은 회사 공간을 새로 만들 수 없고,
  관리자·팀장에게 받은 초대 링크/코드로만 참여합니다.
- 이미 회사 작업공간을 만들었다면 새로 만들지 말고 기존 관리자 화면을 사용합니다.

### 직원 정보 및 과업 작성자

- 직원별 **이름·소속팀·직급/직책**을 등록합니다. 초대 참여 시 필수로 입력하며,
  나중에 '내 직원정보'에서 수정할 수 있습니다.
- 직원 명부에는 해당 3개 항목과 권한(관리자/팀장/팀원)을 표시합니다.
- 세부과업/실행단계 우측 상세 패널은 서버에서 기록한 생성자·생성일,
  최종 수정자·수정일을 표시합니다.
- 작성·수정 이력의 사용자 식별자는 **PostgreSQL 트리거에서 기록**되어,
  브라우저에서 이름/ID를 직접 조작해서 생성자를 바꿀 수 없습니다.
- 최신 DB 적용 전에는 새 직원 프로필 열을 조회할 수 없으므로 3.1 SQL부터 실행해 주세요.

### 후임 최고관리자 인계

1. 현재 최고관리자가 **관리자 설정 → 회사 공동 작업공간 →
   최고관리자 권한 인계**에서 인수할 직원을 지정합니다.
2. **해당 인계자 개인 계정에만** 관리자 인수 요청과 수락 버튼이 표시됩니다.
   인계 요청 기록은 DB RLS로 현 관리자와 지정 인계자 2명만 읽을 수 있습니다.
3. 지정된 인계자가 인수 요청을 수락할 때만 권한이 바뀝니다.
   그 전까지 현 관리자는 기존 권한을 유지하며 요청을 취소할 수 있습니다.
4. 인수 후 새 관리자는 회사 전체 프로젝트를 관리하고,
   이전 관리자는 **일반 팀원**으로 전환되어 배정된 프로젝트 외
   모든 프로젝트의 서버 접근 권한이 차단됩니다.

**중요:** 인수 완료 후에도 이전 관리자가 개인 PC에 별도로 내려받은
JSON 백업이나 스크린샷을 원격 삭제할 수는 없습니다.
회사 비밀번호를 공동 사용하지 말고, 자료 인수 시 개인 백업 파일의
정리·반납도 별도 확인해야 합니다.

### 점검

- 기존 개인 데이터는 개인 계정 클라우드와 백업 파일에 유지됩니다.
- 회사 데이터/관리자 인계 기능은 3.0 및 3.1 SQL을
  **실제 Supabase에 적용해야만** 동작합니다.
- GitHub 코드의 문법·화면 출력 테스트와 SQL 정적 점검은
  데이터베이스에 SQL을 실제 실행한 통합 테스트와는 다릅니다.


### Supabase 3.2: 최고관리자 최초 개설 RLS 오류 수정

기본 공동 작업 SQL(3.0)과 직원·인계 확장 SQL(3.1)을 이미 적용했는데
`new row violates row-level security policy for table "taskflow_workspaces"`
오류가 난다면 [**3.2 수정 SQL**](./supabase_team_v3_2.sql)만 추가 실행합니다.

- 기존 3.1에는 `auth.users.email_confirmed_at is not null` 조건이 있었으나,
  이메일 확인을 요구하지 않는 Supabase Auth 설정에서도 로그인 가능한
  사용자가 있어 이 조건이 최초 개설을 막을 수 있었습니다.
- 수정 후에도 실제 인증된 Supabase 사용자 ID와
  `zotozo12@naver.com` 이메일을 모두 확인합니다.
- 관리자 인계 권한, 작업공간 접근 RLS, 기존 프로젝트 자료는 변경하지 않습니다.
- SQL Editor 결과의 **관리자 계정**과 **이미 생성한 회사 공간 수**를 확인한 뒤
  TaskFlow > 관리자 설정 > **Supabase 설치 상태 확인**을 다시 실행합니다.
- 설계와 정적 검증만으로 실제 사용자의 Supabase Auth 설정을 알 수 없으므로
  실패하면 SQL Editor 결과와 브라우저 오류를 확인해야 합니다.
